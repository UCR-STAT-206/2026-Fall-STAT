Overview

  • We’ll learn about relational databases. Specifically, we use the SQLite engine for SQL accessed through Julia.
  • We’ll practice using a file-based database. No server connections required.
  • We’ll see a few programmatic tools for SQL. These packages provide abstractions around dialects to provide a common interface.
  • Everything we discuss should generalize to other programming languages. The specifics will be tied to the particular language; e.g. Julia vs Python vs R.

The nycflights13 datasets

  • Obtained from https://github.com/tidyverse/nycflights13.
  • Outbound flight information from New York City to US, Puerto Rico, and American Virgin Islands in the year 2013. Includes EWR, JFK, and LGA.
  • There are 336,776 flights recorded in the dataset.

There are multiple tables:

  • flights: all flights that departed from NYC in 2013
  • weather: hourly meterological data for each airport
  • planes: construction information about each plane
  • airports: airport names and locations
  • airlines: translation between two letter carrier codes and names

As suggested by the schematic above, the tables are related to each other:

  • flights connects to planes via a single variable, tailnum.
  • flights connects to airlines through the carrier variable.
  • flights connects to airports in two ways: via the origin and dest variables.
  • flights connects to weather via origin (the location), and year, month, day and hour (the time).

Relational Databases

What is SQL?

SQL (short for Structured Query Language) is a language for managing relational databases with structured data. Its purpose is to facilitate the storage, movement, and updating of data. The structured is less about the data and more about the approach; SQL is based on a mathematical model. Roughly speaking, the components of an SQL are:

  • Data Definition: CREATE, ALTER, DROP, RENAME
  • Data Manipulation: SELECT, INSERT, UPDATE, DELETE
  • Data Control: GRANT, REVOKE
  • Transaction Control: COMMIT, REVOKE, ROLLBACK
  • Data Query: SELECT

In the schema above, there are several tables (airports, flights, and airlines for example) which are related to each other, but whose records do not quite fit together in a single object. For example, the airports table relates to the flights table in terms of the origin and destination fields, but the former contains additional pieces of information such as geographical coordinates. While longitude and latitude define an an origin and destination it is the airport itself that is relevant to flight information.

The relational aspect is due to the theoretical foundations of SQL and other database query languages: It uses relational algebra to define various operations on finite relations, which are defined in terms of tuples and attributes.

  • An attribute \(r_{j}\) is a name paired to a data type; it is a column in a table.
  • A tuple is an ordered set of attributes \(R = (r_{1}, r_{2}, \ldots, r_{p})\); it is a row in a table.
  • A relation is a set of tuples \(\{R_{1}, R_{2}, \ldots, R_{n}\}\); it is a table. Order does not matter.

Here set is a mathematical set. Crucially, this means the names of each attribute must be unique. The purpose of strict, mathematical rigor in these definitions is to design a system that approximates first-order logic. A language based on such a model can be analyzed and understood.

  • Edgar F. Codd famously formalized the concept of a relational database while working at IBM in the 1970s.
  • Theory was used to design a system to implement various operations; e.g. renaming, selecting, joining.
  • The same theory can also be used to optimize queries, increasing execution speed.
  • If you want to master SQL, you must master relational algebra.
  • If you just need to use SQL, it is usually enough to understand the split-apply-combine strategy.

What is SQLite?

SQL comes in many dialects. SQLite itself is a software library that acts as an engine for using SQL. We will use SQLite simply because it can be run in a server-less fashion – it just operates on files on our computer.

Note, however, that other SQL engines operate on a server model: connections to a database are typically between a client and server. Moreover, these systems in general must deal with concurrency – ensuring that multiple simultaneous updates to a database are resolved intelligently.

Why bother?

  • You’re working with data that cannot fit neatly into a single file (e.g. a CSV) because it contains different types of entities (e.g. you actually have multiple tables).
  • Your data is changing/needs to be updated from possibly multiple sources.
  • You’re working in a distributed or streaming setting.
  • You need careful logging of how a database is accessed and updated to enforce certain properties. See also BASE and CAP Theorem.

… and many more compelling reasons. Performance or dealing with Big Data are not necessarily good use cases for SQL. At the end we’ll look at alternatives for those kinds of scenarios.

Building a Database

This extended example uses the SQLite.jl package, which is a wrapper for the SQLite engine. We’ll use it through DBInterface.jl to make our code more generic and less specific to particular engines and Julia packages.

  • See JuliaDatabases for an overview of Julia packages for SQL. It is not an exhaustive list.

Obtaining the Data

We installed the nycflights13 package in R and will now load it to make the various tables available (instead of manually downloading).

# R Code
library(nycflights13)
flights |> head(n = 10)

Now we’ll retrieve the tables on the Julia side.

# Back to Julia
flights = rcopy(R"flights")
weather = rcopy(R"weather")
planes = rcopy(R"planes")
airports = rcopy(R"airports")
airlines = rcopy(R"airlines")

first(flights, 10)

Note that columns with a ? next to the type information hint at explicitly missing values.

Connecting to a Database

First we need to establish a connection to a database. This is done through SQLite.DB.

con = DBInterface.connect(SQLite.DB, "nycflights13.db")
  • If we provide an argument: The database lives in a file. Some RAM is used up as we interact with the database.
  • Otherwise: The entire database is stored in-memory, meaning you’ll use up RAM to store the entire database.
  • There are more generic options via URIs.

Initialization

Starting from scratch

The CREATE TABLE statement allows us to instantiate a new table in our database. Then we can execute INSERT INTO statements to populate the table.

# Delete the table if it already exists
DBInterface.execute(con, "DROP TABLE IF EXISTS airports")

# Then proceed with our example
DBInterface.execute(con,
  "CREATE TABLE airports (faa TEXT, name TEXT, lat REAL, lon REAL, alt REAL, tz INT, dst TEXT, tzone TEXT)"
)
DBInterface.execute(con,
  "INSERT INTO airports VALUES ('04G', 'Lansdowne Airport', 41.1, -80.6, 1044, -5, 'A', 'America/New_York')" 
)

Most SQL interface packages will return a cursor that allows the caller to iterate over the relations returned by an executed query. The CREATE TABLE and INSERT INTO statements do not return relations, so we’ll turn to SELECT * FROM for an example:

for row in DBInterface.execute(con, "SELECT * FROM airports")
  attrs = propertynames(row)
  foreach(attr -> println("$(attr): $(getproperty(row, attr))"), attrs)
end
  • propertynames(row) gives us the attributes for the particular relation (row).
  • getproperty(row, attr) returns the value for the specified attribute attr.
  • If we already know the attribute names, we could just as easily write (Julia) code like row.faa or row[1] instead.

Alternatively, we can pipe |> the cursor to table-like types (i.e. that implement the Tables.jl specification) to display our results:

DBInterface.execute(con, "SELECT * FROM airports") |> DataFrame

Loading from a source

First let’s clear the database for the sake of our example.

tablenames = ["flights", "weather", "planes", "airports", "airlines"]
for tablename in tablenames
  DBInterface.execute(con, "DROP TABLE IF EXISTS $(tablename)")
end

Now load it. DBInterface.jl does not provide an abstraction for this, so we’ll have to use an SQLite.jl command directly:

SQLite.load!(flights, con, "flights")
SQLite.load!(weather, con, "weather")
SQLite.load!(planes, con, "planes")
SQLite.load!(airports, con, "airports")
SQLite.load!(airlines, con, "airlines")

Display the tables available in the database by querying the schema:

DBInterface.execute(con, """
SELECT
  name
FROM
  sqlite_master
WHERE
  type = 'table' AND
  name NOT LIKE 'sqlite_%'
""") |> DataFrame

If you replace name above with *, you will be able to see every column in the database schema.

  • type : index or table.
  • name : index or table name
  • tbl_name : Name of the table
  • rootpage : internal information to SQLite.
  • sql : The SQL statement which would create the given table.

Example Queries

Let’s implement a simple wrapper to avoid typing the same lines of code over and over.

function example(context, query)
  DBInterface.execute(context, query) |> DataFrame
end

SELECT

SELECT columns or computations
  FROM table
  WHERE condition
  GROUP BY columns
  HAVING condition
  ORDER BY column [ASC | DESC]
  LIMIT offset, count;

Display the carrier, flight number, origin, and destination of every flight:

example(con, """
SELECT carrier, flight, tailnum, origin, dest
  FROM flights
""")

Display the flights table (all columns) but limited to 10 rows.

example(con, "SELECT * FROM flights LIMIT 10")
first(flights, 10) # DataFrames.jl equivalent

Ditto, but order the relations according to the arr_delay attribute.

example(con, "SELECT * FROM flights ORDER BY arr_delay LIMIT 10")
first(sort(flights, :arr_delay), 10)

Ditto, but do it in descending order.

example(con, "SELECT * FROM flights ORDER BY arr_delay DESC LIMIT 10")
first(sort(flights, :arr_delay, rev = true), 10)

WHERE

Filtering can be achieved using this keyword. Let’s identify the flights with at least 2 hour arrival delays and negative departure delays (early departure). It is at this level of complexity that one starts to see possible performance differences so let’s do some light benchmarking, too.

@time begin
  example(con, """SELECT origin, dest, arr_delay, dep_delay
    FROM flights
    WHERE arr_delay >= 120 AND dep_delay < 0
  """)
end

Most DataFrame-like implementations use eager evaluation, meaning many temporary copies are created in executing complex queries.

@time begin
  tmp1 = dropmissing(flights)
  tmp2 = filter("arr_delay" => >=(120), tmp1)
  tmp3 = filter("dep_delay" => <(0), tmp2)
  select(tmp3, ["origin", "dest", "arr_delay", "dep_delay"])
end

We can do a little better by executing the subset before filtering, leveraging mutation, and fusing the filter operations:

# avoid performance penalty by using a non-anonymous function
is_interesting(arr_delay, dep_delay) = arr_delay >= 120 && dep_delay < 0

@time begin
  tmp1 = dropmissing(flights)
  select!(tmp1, ["origin", "dest", "arr_delay", "dep_delay"])
  filter!([:arr_delay, :dep_delay] => is_interesting, tmp1)
end

Takeaway message

  • If your SQL engine has a query optimizer, it’s worth learning how to use it if you’re working with huge databases + queries.
  • You generally cannot control how an SQL engine evaluates your queries, but they’ll try to do the “right” thing. A programming language usually exposes tools in the language to achieve just that.

Computations

SQL dialects usually offer some support for basic arithmetic and descriptive statistics.

example(con, """
SELECT distance, air_time, distance / air_time AS speed
  FROM flights
  ORDER BY speed DESC LIMIT 10
""")

GROUP BY, HAVING

  • Aggregate relations with GROUP BY
  • Pre-aggregation selection with WHERE
  • Post-aggregation selection with HAVING
example(con, """
SELECT dest, AVG(arr_delay) AS mean_arr_delay 
  FROM flights
  WHERE arr_delay > 0
  GROUP BY dest
  HAVING mean_arr_delay > 60
""")

JOIN

SELECT * FROM x INNER JOIN y USING (z)
SELECT * FROM x LEFT OUTER JOIN y USING (z)
SELECT * FROM x RIGHT OUTER JOIN y USING (z)
SELECT * FROM x FULL OUTER JOIN y USING (z)
example(con, """
SELECT year, month, day, carrier, flight
  FROM flights INNER JOIN airlines
  USING(carrier)
""")

The USING (z) clause can be replaced by

  • The ON x.z == y.z clause, which allows different key column names, and relations will be filtered before joining.
  • The WHERE x.z == y.z clause, where relations will be filtered after a join has taken place.
example(con, """
SELECT year, month, day, carrier, flight, origin, dest
  FROM flights
  INNER JOIN airports
    ON flights.dest == airports.faa 
  WHERE flights.origin == "JFK"
    AND airports.tz <= -8
""")

  • NoSQL: Non-relational database management system.
  • DuckDB: Focused on ‘analytics’. See the Julia examples here.
  • SQLREPL.jl: Adds a PostgreSQL REPL mode to the Julia REPL.
  • TidierDB.jl: A Julia implementation of dbplyr in R.

Beyond SQL

Earlier we mentioned that SQL is not exactly a solution to Big Data. This is because, while different implementation use all sorts of tricks to accelerate their queries, the dialects are designed around abstractions for databases. They have little concern for how data will be used (e.g. to plot or to feed an ML pipeline).

Instead, there are specialized platforms to support efficient distributed computing. For example, the Apache Spark platform is designed around a Resilient Distributed Dataset (RDD) model to facilitate streaming workflows or iterative algorithms. The Apache Spark project provides bindings in R, Python, and many other programming languages. Julia support is through third-party packages, such as SparkSQL.jl.

The DuckDB system is another alternative. While on the surface it may resemble another SQL dialect, it is focused on computation (analytics) rather than transactions (ensuring valid database states between updates).

When SQL is not the right tool

These suggestions are framed as alternatives to using SQL, but they are good tools to be aware about for exporting data from a database for local analysis.

Data does not fit in memory

Do you really need to load the full data into RAM? If not, you have a few options.

Use memory-mapped options

Memory-mapped solutions use disk space instead of RAM.

Store the data in binary formats

The Parquet, Arrow, and HDF5 file types are available in Python, R, and Julia.

Arrow.write("flights.arrow", flights)

For example, Arrow provides a memory-mapped solution to reading tabular data:

arrow_flights = Arrow.Table("flights.arrow")

Dataframe-like libraries also tend to support compressed file formats (e.g. zip or gz), which may be combined with memory-mapped solutions.

CSV.write("flights.csv.gz", flights; compress = true)

Chunk your data

Consider partitioning your data source into chunks; e.g. separate files. Some Dataframe-like libraries provide support with chunking without manually partitioning the data:

# Read approx 10,000 items in 4 chunks.
chunks = CSV.Chunks("flights.csv.gz"; limit = 10^4, ntasks = 4)

for (k, file) in enumerate(chunks)
  df = DataFrame(file)
  display(describe(df))
end

Data does not consist of relations

Numerical experiments generate data. Large-scale experiments may yield “big data” but it need not be tabular; e.g. a custom type. [Serialization] tools like JLD2.jl offer a way to save and load your data in its native format, using both compression and memory-mapping.

Similar tools exists in Python (e.g. pickle) and R (e.g. RDS for single objects and RDA for multiple objects)

struct MyType{T}
  data::T
end
MyType(1.0)
MyType([1,2,3])
JLD2.save_object("example.jld2", MyType([1, 2, 3]))
JLD2.load_object("example.jld2")
