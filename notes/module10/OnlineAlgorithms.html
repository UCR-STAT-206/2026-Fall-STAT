Reprise: Online Mean

Earlier in the course we derived a straightforward algorithm for computing a sample mean in a streaming setting. The usual estimator

\[ \mu_{n+1} = \frac{1}{n+1} \sum_{i=1}^{n+1} x_{i}, \]

can be written in the recursive form

\[ \mu_{n+1} = \frac{1}{n+1} x_{n+1} + \frac{n}{n+1} \mu_{n}, \]

allowing one to compute an estimate of the sample mean \(\mu_{n+1}\) without having full access to the sample of size \(n+1\). The streaming setting comes about due to various reasons. We will explore 3 scenarios that force us to work with online algorithms:

  1. We are working with Big Data. There is no hope of loading the full sample to compute an estimator \(\theta_{n}\) for \(\theta\) that we are interested in.
  2. We are working with a real-time or distributed system. We don’t have full access to the data because it is being generated as we work. We still need/want to monitor the data in real-time.
  3. The underlying generative process is non-stationary. The distribution of the data itself might be changing over time, and so the “true” quantity of interest, \(\theta\), is itself changing over time. In this setting it may be helpful to change notation to \(\theta_{t}\). We’ll adopt this notation moving forward.

OnlineStats.jl

OnlineStats.jl is a collaborative open-source project lead by Josh Day. From the documentation:

OnlineStats does statistics and data visualization for big/streaming data via online algorithms. Each algorithm:

  1. processes data one observation at a time.
  2. uses O(1) memory.

Object-Oriented Programming…?

Various statistics and models are implemented as a concrete OnlineStat{T} object, where T is a type parameter indicating the underlying data type of a single observation.

n = 100
rng = Xoshiro(206)
x = rand(rng, Normal(), n)
θ = Mean(Float64) # or just Mean(eltype(x))

We can query the supertype of this object’s type:

typeof(θ)
supertype(typeof(θ))

Here we see that the Mean type appears to have an additional type parameter. We’ll return to it later. Moving forward, you should understand we think about Julia objects not in terms of their fields (i.e. how the ‘class’ is designed) but by their types. Type parameters in composite types allow us to define a family of types.

typeof(x)
supertype(typeof(x))

Julia uses the type information in multiple dispatch to implement polymorphic behavior.

Overview of the Package

The OnlineStats.jl package provides

  1. several types for computing individual statistics/model parameters,
  2. an interface for updating and retrieving values of an OnlineStat object,
  3. an interface for merging OnlineStat objects (e.g. in parallel processing), and
  4. an interface for tracking collections of OnlineStat objects.

Working with a data stream

Last time we created a compressed file flights.csv.gz of the nycflights13 data. Using the chunking capabilities of the CSV package, we can

  1. open up a stream containing a chunk of the data, and
  2. use the chunk to iteratively update our estimates of particular statistics.

Let’s compute the mean and variance in both the arrival and departure delays:

arr_delay = Series(Mean(), Variance()) # Series: statistics applied to the *same* data stream
dep_delay = Series(Mean(), Variance())
delays = Group(arr_delay, dep_delay)   # Group: statistics applied to *different* data streams

Our estimators will simply ignore missing data. As such, the two statistics will be based on a different number of observations.

# Data *may* be read in compressed format without type information using CSV.Rows.
# We can provide a type specification to help the parser in this case.
type_spec = Dict(
  :arr_delay => Union{Missing, Float64},
  :dep_delay => Union{Missing, Float64},
)

# first run will hit the pre-compilation penalty
@time for row in CSV.Rows("flights.csv.gz", types = type_spec, reusebuffer = true)
  if !ismissing(row.arr_delay)
    fit!(delays[1], row.arr_delay)
  end
  if !ismissing(row.dep_delay)
    fit!(delays[2], row.dep_delay)
  end
end

delays

Why is this so complicated?

  • type_spec: Helps the parser infer type information. Without it, this loop took over 30 seconds on the first run. This version cuts it down to 1 second on pre-compilation. In any language, type inference has a cost.
  • reusebuffer = true: A single object is used to retrieve and represent the data along each row.

Parallel processing of a data stream

Suppose we have a large data stream and want to process it in parallel. Our formula for the sample mean can be expressed in terms of batches which are computed using some form of parallelism:

\[ \theta = \alpha_{1} \theta_{n_{1}} + \alpha_{2} \theta_{n_{2}} + \ldots + \alpha_{m} \theta_{n_{m}} \]

Here the sample size \(n = \sum_{i=1}^{m} n_{i}\) and the \(\alpha_{i}\) are weights that make the expression valid. The idea is to compute each \(\theta_{n_{i}}\) in parallel and then merge!() their results. Various forms of parallel processing are built into the Julia language. Here we’ll use multi-threading.

Warning
  1. Not every statistic \(\theta\) has a valid representation given above. In some cases, the form above is merely a smooth approximation, usually constructed with the \(\alpha_{i}\) being convex weights.
  2. Parallel Algorithm \(\neq\) Faster Algorithm. The example below does not use the CSV example because I/O, the process of reading (and parsing) a file, will bottleneck a multi-threaded algorithm. Instead, we need a distributed algorithm, so that the I/O itself is done by separate cores, to actually speed up the example.
n = 10^6
nchunks = 10 # matches number of physical cores on current machine
rng = Xoshiro(206)
xdata = rand(rng, Normal(10, 0.5), n)
stats = [Series(Mean(), Variance()) for _ in 1:nchunks]

We cannot use a single OnlineStat because the fit!() operation is not thread-safe. That is, multiple workers may attempt an update on an OnlineStat, creating a race condition. Race conditions usually result in undefined, non-deterministic behavior.

Now break up the iteration space. Fortunately, we can divide the work into even chunks which will play nicely with views of the xdata.

chunk_size = div(n, nchunks)
@show chunk_size
chunks = Iterators.partition(1:n, chunk_size)
collect(chunks)
Note

In practice, parallel algorithms rely on padding arrays to create equally sized chunks of data. Padding and tiling are two techniques used, for example, in writing a good BLAS implemenation.

@time @sync begin
  Threads.@spawn for (k, chunk) in enumerate(chunks)
    xlocal = @view xdata[chunk]
    fit!(stats[k], xlocal)
  end
end
stats
  • @sync creates a code block that waits until any parallel processing terminates.
  • Threads.@spawn creates a task executed by worker threads. There is no guarantee that 1 task = 1 worker, so the work splitting with multiple OnlineStat objects is necessary to avoid various technical issues that can occur in multi-threading (false sharing, cache misses, race conditions).

Each chunk is quite large so we expect each Series to have decent estimates of the sample mean and variance. Let’s merge them now:

θ = stats[1]
@time for k in 2:length(stats)
  merge!(θ, stats[k])
end
θ

Non-Stationary Data

Non-stationary data violate the identically distributed assumption we make in showing that the sample mean is an unbiased estimator for the population mean.

n = 1000
rng = Xoshiro(206)
xdata = [rand(rng, Normal(1e-2 * k, 1.0)) for k in 1:n]
scatter(xdata, xlabel = "Index", ylabel = "Data Value", ms = 4, msw = 0, legend = false)

Here the mean is gradually changing over time, making the mean parameter \(\mu_{t}\) a function of time. Usual estimator is invalid and thus our online algorithm will not accurately track the statistic.

Let’s use the Weights in OnlineStats to explore this idea. The default weighting scheme is EqualWeight() which assign a weight of \(1/t\) to each observation in the sample (even as \(t\) changes). In contrast, the ExponentialWeight() scheme always assigns a weight \(c\) to each new observation. Over time, the effect is that the most recent observation has the most influence.

θ₁ = Trace(Mean(weight = EqualWeight()), 50)
θ₂ = Trace(Mean(weight = ExponentialWeight(0.1)), 50)
traces = Series(θ₁, θ₂)

@gif for xi in xdata
  fit!(traces, xi)
  scatter(xdata, ma = 0.5, ms = 4, msw = 0, label = nothing)
  plot!(θ₂, msw = 0, label = "ExponentialWeight")
  plot!(θ₁, msw = 0, label = "EqualWeight")
end every 20
scatter(xdata, ma = 0.5, ms = 4, msw = 0, label = nothing)
plot!(θ₂, msw = 0, label = "ExponentialWeight")
plot!(θ₁, msw = 0, label = "EqualWeight")

Emphasizing the most recent observation leads to a good estimator of the time-varying mean.

The motivation for different weight schemes can be seen in our earlier formula for \(\mu_{t+1}\):

\[ \mu_{t+1} = \frac{1}{t+1} x_{t+1} + \frac{t}{t+1} \mu_{t} = \gamma_{t+1} x_{t+1} + (1 - \gamma_{t+1}) \mu_{t}. \]

Here \(\gamma_{t+1} \in (0, 1)\) can take on any form in principle. Restricting the weights to be convex weights makes the estimator a convex combination of (i) the data and (ii) the previous estimates.

Extending the scheme to an arbitrary statistic \(\theta_{t}\), it can be viewed as an averaged operator that is generally a smooth approximation. This idea is studied and used in designing algorithms through the lens of nonlinear optimization; see for example Combettes and Yamada.

Case Study: Histograms

How can we fit a histogram to a data stream?

Background

Many problems in statistics are challenging precisely because at least one key distribution is either unknown or unavailable. Otherwise, many statistics and quantities of interest easy to calculate. Nonparametric statistics grapples with unknown objects directly. There are several flavors of this branch of statistics, including

  • distribution-free: One avoids making assumptions about data or quantities derived from data.
  • model-free: One avoids making assumptions about relationships between dependent and independent variables. That is, we try to avoid introducing anything that looks like a model parameter.

These definitions are not rigid. The essence of nonparametric statistics is to make as few assumptions as possible.

What is a histogram?

Fitting a histogram to univariate data is an instance of nonparametric estimation – we are not choosing from a particular family of distributions (e.g. fitting a Poisson distribution) but rather estimating the density function itself.

Given the support of some univariate data (let’s say a bounded subset \(S \subset \mathbb{R}\)), we partition it into non-overlapping intervals of the form \([a_{k}, b_{k})\) so that \(S = \cup_{k \in \mathcal{I}} [a_{k}, b_{k})\). Then for each interval we compute the counts \[ N_{k} = \sum_{i = 1}^{n} 1\{X_{i} \in [a_{k}, b_{k})\}, \qquad \sum_{k \in \mathcal{I}} N_{k} = n, \] effectively binning the data. The collection of intervals \(\{[a_{k}, b_{k})\}_{k \in \mathcal{I}}\) can therefore be thought of as a compressed representation of the sample \(\{x_{i}\}_{i=1}^{n}\).

  • Using too few bins, i.e. \(|\mathcal{I}|\) too small, leads to a poor estimate.
  • Using too many sacrifices efficiency (computational and statistical).
  • Regardless of our choice, we can always scale the \(N_{k}\) to make the histogram represent frequencies, probabilities, or a proper density.
  • Regardless of our choice, we’re assuming that \(S\) is known!

The Hist type in OnlineStats implements this approach.

n = 10^3
rng = Xoshiro(206)
true_dist = Normal(0.0, 1.0)
xdata = rand(rng, true_dist, n)
plot(true_dist, legend = nothing, title = "True Distribution")
scatter!(xdata, repeat([0.0], n), marker = :vline, markeralpha = 0.25)
function demo_histogram(H, xdata; kwargs...)
  fit!(H, xdata)
  display(H)
  for f in (mean, var, extrema, quantile)
    @show f, f(H)
  end
  plot(H; kwargs...)
end
a, b, bwidth = -3.0, 3.0, 0.5
H₁ = Hist(a:bwidth:b)
demo_histogram(H₁, xdata, legend = false, title = "Bin Width: $(bwidth)")
a, b, bwidth = -3.0, 3.0, 0.1
H₂ = Hist(a:bwidth:b)
demo_histogram(H₂, xdata, legend = false, title = "Bin Width = $(bwidth)")
  • The tails approach 0 fairly quickly (depending on variance of distribution).
  • Our sample has a few observations \(|x_{i}| \ge 3\). These are ignored because they do not fall within any of the bins.
  • In principle, we could identify the “best” histogram by comparing against the true density (e.g. minimize \(L_{2}\) error).
  • Although neither histogram is particularly bad, it’s clear that we’re paying a price for assuming we’ve chosen the “right” number of kinds of bins.

Fix only the number of bins

If we avoid specifying the bin edges (intervals) and instead fix the number of bins, we might construct a histogram in a data-adaptive manner. Let’s simplify by fixing the number of edges, \(K\), and limiting ourselves to equally spaced bins. The KHist type in OnlineStats implements this idea. This online algorithm for histogram estimation is attributed to a 2010 JMLR paper on decision trees.

K = 11
H₃ = KHist(K)
demo_histogram(H₃, xdata, legend = false, title = "KHist with $(K-1) bins")
K = 101
H₄ = KHist(K)
demo_histogram(H₄, xdata, legend = false, title = "KHist with $(K-1) bins")

This estimator does not have bin widths becauase it only tracks the number of observations that surround the histogram’s internal points.

Keeping track of bin widths

The ExpandingHist adaptively determines bin edges from data. The only requirement is that the number of bins must be even because it is constructed by iteratively doubling the bin edges as needed.

B = 10
H₅ = ExpandingHist(B)
demo_histogram(H₅, xdata, legend = false, title = "ExpandingHist with $(B) bins")
B = 100
H₆ = ExpandingHist(B)
demo_histogram(H₆, xdata, legend = false, title = "ExpandingHist with $(B) bins")

Notice that this approach correctly handles the “extreme” point near \(-4\).

Recovering the density

Regardless of the choice of histogram estimator, a kernel function can be used to recover a smooth estimate of the underlying density. The specific method used is the Average Shifted Histogram.

histograms = Series(Ash(H₁), Ash(H₂), Ash(H₃), Ash(H₄), Ash(H₅), Ash(H₆))
plot(histograms, size = (900, 600))

ImplementingExpandingHist

The idea is simple:

  1. A user specifies the number of bins \(b\) which must be even. This information is used to construct \(b-1\) left-closed bins and \(1\) closed bin (the rightmost one):

    [a, b), [b, c), [c, d), [d, e]

    This numbers \(a\), \(b\), \(c\), \(d\), and \(e\) are the edges.

  2. Now suppose we start with the following bin counts:

    |1|2|5|3|

    where the extreme edges are \(a\) and \(e\).

  3. We observe a data point \(y\) and so we must update the histogram. There are 3 cases to consider:

    • Case: \(a \le y \le b\): The point lies inside the current limits of the histogram, so we simply find the bin it belongs to.

         *
   ↓
|1|2|5|3|   --->   |1|3|5|3|

    • Case: \(y > b\): The point lies outside (to the right) of bin edges.

      |1|2|5|3|       *

      We expand each bin to the right by doubling the edges. Adjacent bins merge with their neighbors to the right. Multiple expansions (doublings) may be required to cover the data:

      |1|2|5|3|       *
 \ / \ / \ / \ /
| 3 | 8 | 0 | 1 |

    • Case: \(y < a\): This case is symmetric to the previous case, except the histogram expands to the left.

The source code is available here.

Representing a histogram

Let’s implement our own Julia type to represent a histogram. We need to track 3 objects

  • n: the number of observations the histogram has “seen” so far. We’ll initialize this to \(0\).
  • edges: an ordered collection of the bin edges. We’ll initialize this to \(0\)s.
  • counts: an ordered collection of the bin counts, aligning with the bin edges. Again, we’ll initialize this to \(0\)s.
mutable struct MyAdaptiveHist
  n::Int
  edges::Vector{Float64}
  counts::Vector{Int}
end
  • The mutable keyword is needed because we’ll need to update n. Otherwise instances of MyAdaptiveHist would be immutable.
  • The field::type pairs inside the struct ... end define a Julia type.
  • The default constructor is MyAdaptiveHist(n, edges, counts), where n must be an Int, edges must be a Vector{Float64}, and counts must be a Vector{Int}.

We only need a user to tell us the number of bins, \(B\). Let’s write an outer constructor for this purpose.

function MyAdaptiveHist(B::Int)
  if isodd(B)
    error("The number of bins must be even! Got: $(B)")
  end
  n, edges, counts = 0, zeros(Float64, B+1), zeros(Int, B)
  return MyAdaptiveHist(n, edges, counts)
end

Let’s make sure the constructor works.

H = MyAdaptiveHist(10)

We can access the fields or type data directly with object.fieldname or programmatically as getproperty(object, :fieldname). It is crucial that the second argument is a Symbol type, e.g. :counts.

  • We designed MyAdaptiveHist to start with n = 0. That’s why we update this value as soon as we validate the input data.
  • We work out the three cases by considering (i) whether the histogram is currently empty, (ii) whether the histogram has only seen one distinct value, and (iii) whether the histogram needs to expand.
  • The type is mutable, so we’ll write our helper functions with mutation in mind.

Expanding the histogram

Aside from update!(), the expand!() function is the most important functionality.

  • This needs to detect which direction to expand the bin edges.
  • The operation must update the edges and counts fields.
  • We will write this function in such a way that it handles the possibility of not expanding.
  • In the code below, K represents the number of times we double the edges to ensure \(x \in [a, b]\). We can use this invariant to calculate K.
function expand!(H::MyAdaptiveHist, x)
  # Retrieve extreme edges
  a, b = extrema(H.edges)

  # Compute the width of the histogram
  w = b - a
  if w == 0
    error("expand!() should not be called on a 0-width histogram.")
  end

  # Calculate the middle bin index, M
  B = length(H.counts)
  M = div(B, 2)
  
  if x > b
    # Expand to the right by finding K such that
    # x <= a + 2^K * w
    K = ceil(Int, log2((x - a) / w))
    H.edges .= range(a, a + (2 ^ K) * w, length = B + 1)
    merge_right!(H.counts, K, M)
  elseif x < a
    # Expand to the left by finding K such that
    # x >= b - 2^K * w
    K = ceil(log2((b - x) / w))
    H.edges .= range(b - (2 ^ K) * w, b, length = B + 1)
    merge_left!(H.counts, K, M)
  end

  return H
end

Merging the bins after expanding

Regardless of whether we expand left or right, we may need to sweep the counts vector multiple times to correctly propagate bin counts.

  • We sweep \(M = B / 2\) times at most.
  • To see why, think about what happens to the bin edges for the middle bin after \(1, 2, \ldots, M\) doublings.

To merge bin counts to the left, we start at the right-most bin and move towards the left one.

function merge_left!(counts, K, M)
  B = length(counts)
  for k in 1:min(K, M), i in 0:(B-1)
    if i+1 <= M
      counts[B-i] = counts[B-2*i] + counts[B-2*i-1]
    else
      counts[B-i] = 0
    end
  end
  return counts
end

To merge right, we start at the left-most bin and move towards the right.

function merge_right!(counts, K, M)
  B = length(counts)
  for k in 1:min(K, M), i in 1:B
    if i <= M
      counts[i] = counts[2*i-1] + counts[2*i]
    else
      counts[i] = 0
    end
  end
  return counts
end

Finding the correct bin

Let’s write a function to look up which bin an observation falls into. We can use searchsortedlast() on the edges field since it is assumed to be in sorted order, making the search operation efficient through bisection.

Letting \(a\) and \(b\) with \(a < b\) denote the extreme edges of the bin edges, we consider the following cases:

  1. If \(x < a\) or \(x > b\) something has gone wrong.
  2. If \(x = a\) or \(x = b\) return \(1\) or \(B\), respectively.
  3. Otherwise, return the particular bin index.
function find_bin(edges, x)
  B = length(edges) - 1
  a, b = extrema(edges)

  # error cases
  x < a || x > b && error("The value $(x) should not be out of bounds for [$(a),$(b)].")

  # valid cases
  x == a && return 1
  x == b && return B
  return searchsortedlast(edges, x)
end

Putting it all together

function update!(H::MyAdaptiveHist, x::Number)
  # Validate the new datum x
  if isinf(x) || isnan(x) || ismissing(x) || isnothing(x)
    error("Invalid input $(x) of type $(typeof(x)).")
  end

  # Retrieve parameters and update nobs.
  n, B = H.n + 1, length(H.counts)
  H.n = n

  if n == 1
    # Case: Starting with a fresh histogram.
    # There is only 1 bin, so all edges are equal to each other.
    H.edges .= x
    H.counts[1] = 1
  elseif all(isequal(first(H.edges)), H.edges)
    # Case: We've never expanded the histogram before, but its trivial.
    a = H.edges[1]
    if x == a
      # It's the same value so we don't need to expand.
      H.counts[1] += 1
    elseif x < a
      # Expand once to the left.
      H.edges .= range(x, a, length = B+1)
      H.counts[B] = H.counts[1]
      H.counts[1] = 1
    else x > a
      # Expand once to the right.
      H.edges .= range(a, x, length = B+1)
      H.counts[B] = 1
    end
  else
    # Case: We may need to expand multiple times before we update the counts.
    expand!(H, x)
    k = find_bin(H.edges, x)
    H.counts[k] += 1
  end

  return H
end

Lastly, let’s add a method to handle batches. We’ll take the naive approach but you should think about a more efficient implementation.

function update!(H::MyAdaptiveHist, x::AbstractVector)
  for xi in x
    update!(H, xi)
  end
  return H
end

Add a plotting recipe

@recipe function f(::Type{MyAdaptiveHist}, H::MyAdaptiveHist)
  # find the first and last nonzero counts
  start = findfirst(>(0), H.counts)
  stop = findlast(>(0), H.counts)
  edges = H.edges[start:stop+1]
  counts = H.counts[start:stop]
  return StatsBase.Histogram(edges, counts)
end
