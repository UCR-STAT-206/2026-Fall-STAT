Functions

Goals

  1. Understand basic syntax of a Julia function.
  2. Understand Julia’s scoping rules.
  3. Develop an awareness of how Julia functions can be used, manipulated, and leveraged.
  4. Develop a mental model for writing functions in Julia.

Overview

Functions are the basic units by which we assemble solutions to complex problems. This is especially true in R and Julia, as the languages strongly favor a Functional Programming (FP) style. These languages greatly benefit from ideas in other FP languages (e.g. Lisp) that came before and which evolved concurrently. One key aspect of FP is that functions are treated like any other object in the language (first-class citizens).

Note

For the Python users, the language favors a particular flavor of object-oriented programming that puts lets emphasis on functions/methods and more on classes. But functions remain important!

Syntax and Semantics

function func(req1, req2; key1=dflt1, key2=dflt2)
  # do stuff
  return out1, out2, out3
end
  • Required arguments are separated by a comma and use positional notation.
  • Optional arguments need a default value in the signature.
  • Semicolons are not required in a function call. It is used to separate positional arguments from keyword arguments.
  • A return statement is optional, but highly encouraged in STAT 206.
  • If your function needs to return multiple values, use a Tuple, Dict, or NamedTuple.

Anonymous Functions

Anonymous functions are functions without a name.

  • These are short functions in terms of code length.
  • Used only once and have no reuse value.
  • Are commonly used in collection functions or list comprehensions.

Important

Function names ending with ! indicate that the function mutates at least one argument, typically the first. This is strictly a convention; adding ! to the end of a Julia function does nothing semantically.

Variable scope and rules

Variable scope and the associated rules defining scope are all about what functions can “see” and “do”.

  • Each function has its own environment, or local scope.
  • Names here override names in the global scope.
  • Internal environment starts with the named arguments.
  • If your computer encounters an undefined name in a function, it looks for it in the environment of the next outer scope where the function was defined. This is known as lexical scope.

Julia, R, and Python all use some variation of these rules for variable scope. That is, they all use lexical scope to resolve any “free” variables/symbols.

Julia’s scope rules are more or less straightforward. Below are some Julia-specific quirks:

  • Everything lives in the Main module, but default. It is the enclosing global scope for interactive environments; e.g. if you are working in the Julia REPL.
  • Global references must be declared using global for consistent behavior. Otherwise, global references will change depending on context, due to hard vs soft scoping.
  • Julia allows mutation of mutable types. This reason alone is a good reason to avoid global references at all costs.
  • Scalars are immutable, as are many other constructs. You cannot change their content.
  • An Array object is mutable, so changing the content of an Array instance persists outside a function call.
  • Remember that x = <expr> binds the RHS to the left; x .= <expr> fills the LHS with the RHS.
TipAvoid global variables!
  • Reduces risk of confusion and error.
  • Exception: Reserve global variables for true universal concepts like \(\pi\).
  • Exception: Allocating work buffers in large and sophisticated libraries like BLAS/LAPACK.

Example: Using a global variable

x = 7
y = ['A', 'C', 'G', 'T', 'U']

function adder(y)
  global x # specify a global reference
  x = x + y
  return x
end

Using functions

Nesting

Functions can be nested. In the example below, the outerfunction() can be invoked in the enclosing scope, whereas the innerfunction() is only visible within outerfunction().

function outerfunction()
  # do some outer stuff
  function innerfunction()
    # do inner stuff
    # can access prior outer definitions
  end
  # do more outer stuff
end
outerfunction (generic function with 1 method)
TipWhat’s the use case?

It is sometimes advantageous to hide helper functions where they are used, especially if they are not used elsewhere. Inner functions are also used to create closures, functions that “fix” some arguments to another function. We will discuss these at a later date.

Recursion

Julia supports recursive function definitions.

A successful recursive implementation of a function requires two key ingredients:

  1. A base case. How do we know when to stop recursion?
  2. A recursive step. How do we build the next item in the recursion?

Without a base case, a recursive function will create too many calls to itself and trigger a StackOverflow exception. This is a protection built into programming langauges to prevent “runaway code” that never terminates.

Example: Factorial

The following code implements the factorial function, \(n! = n \times (n-1) \times \ldots \times 2 \times 1\).

function myfactorial(n)
  if n > 1
    # recursive step
    return n * myfactorial(n-1)
  else
    # base case; treats x! = 1 for any x <= 0.
    return 1
  end
end
myfactorial (generic function with 1 method)
@show myfactorial(3)
@show myfactorial(6);
myfactorial(3) = 6
myfactorial(6) = 720

How to write (Julia) functions

Treat function signatures as interfaces

Interfaces are the inputs or arguments; the outputs or return value.

  • An interface tells the caller what is required.
  • Outside perspective: Try to avoid caring about what is inside a function or how it carries out its work.
    • Calls other functions: ifelse(), abs(), operators ^ and >, and could also call other functions we’ve written.
    • Keep the internals orthogonal to the external; that’s encapsulation.
  • return says what the output is; alternately, return the last evaluation.
    • We often do not need to care about this; just use return to be explicit!
  • Comments: Not required but a good idea.
    • Helps document what kinds of inputs are required.
    • Julia and R are dynamic languages. No constructs to enforce types in signatures.
    • Documentation/comments should signal what is/isn’t allowed.

What should be a function?

  • Things you’re going to re-run, especially if it will be re-run with changes.
  • Chunks of code you keep highlighting and hitting return on.
  • Chunks of code which are small parts of a larger analysis or process.
  • Chunks of code which are very similar to other chunks.

Named and default arguments

Consider the “robust” loss function

\[ \psi(x) = \begin{cases} 2 |x| - 1, & x^{2} > 1 \\ x^{2}, & x^{2} \le 1 \end{cases}. \]

We define two versions of this function below:

# Robust loss function for outlier-resistant regression
# Inputs: vector of numbers (x)
# Outputs: vector with x^2 for small entries, |x| for large ones
function psi1(x)
  psi = ifelse(x^2 > 1, 2*abs(x) - 1, x^2)
  return psi
end

# Robust loss function for outlier-resistant regression
# Inputs: vector of numbers (x), scale for crossover (c)
# Outputs: vector with x^2 for small entries, 2c|x|-c^2 for large ones
function psi2(x; c::Real = 1.0)
  psi = ifelse(x^2 > c^2, 2*c*abs(x) - c^2, x^2)
  return psi
end
psi2 (generic function with 1 method)

Let’s check that they are the same when \(c=1\):

z = 1.3
psi1(z) ≈ psi2(z; c = 1.0)
true

Notice that default values are used whenever named arguments are missing:

psi2(z; c = 1.0) ≈ psi2(z)
true

Julia enforces order in positional arguments due to its multiple dispatch system. Can’t mimic what you see on the R side for shuffling arguments.

Checking arguments

Problem: We see odd behavior when arguments are not specified as expected.

psi2(z; c = Float64[1, 1, 1, 10])
TypeError: in keyword argument c, expected Real, got a value of type Vector{Float64}

Solution: Put sanity checks in the code. Ideally, put any input validation at the top of the function body.

function psi3(x; c::Union{Real,AbstractArray{<:Real}} = 1)
  if !(c isa Number)
    error("Parameter `c` should be given as a number. Did you mean `psi3.(x; c = c)`?)")
  elseif c < 0
    error("Parameter `c` should be positive. Got $(c).")
  end
  return psi2(x; c = c) # now this is safe!
end

Encapsulation: Respect the interfaces!

  • Interfaces mark out a controlled environment for our code.
  • A function interacts with the rest of a system only at the interface.
  • Similarly, the “output” should only be through the return value.
    • That means avoiding side-effects, which are modifications to some external state not defined inside a function.

Your goal in writing a function is to achieve encapsulation: separate what your function does from how it implements its task.

  • It should do one and only one thing as well as possible.
  • If your function needs to modify some state/data, then that state/data ought to be arguments to the function.
  • Information that is unrelated to what a function does should be minimized as much as possible.
