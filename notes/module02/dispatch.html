Multiple Dispatch

Goals

  1. Be able to describe polymorphism in the context of programming.
  2. Understand multiple dispatch as a mechanism for implementing polymorphic behavior in Julia.
  3. Practice using multiple dispatch in implementing simple algorithms.

Before reading these notes

  • Review notes on Julia’s type system.
  • Watch part of Stefan Karpinski’s JuliaCon 2019 talk on The Unreasonable Effectiveness of Multiple Dispatch. Up to at least 12:56, if not 25:16.

Polymorphism

Polymorphism in a programming language is about allowing a function to exhibit different behaviors depending on the types that it sees.

  • For example, in Julia we’ve seen that the + operator implements the usual notion of addition for floating point numbers, integers, complex numbers, and various array objects. In these instances, the internal logic changes depending on the type of objects you add together.
  • On the other hand, the role of print() and println() is to take objects and display them in the standard output stream. There may be significant differences in converting specific objects to a textual representation, but these functions follow a uniform logic.

Three major forms of polymorphism are:

  1. Ad hoc: You write a fancy_function() that serves as a common interface for a specific computation or concept. You implement the interface/concept for specific types as you see fit.
    • Examples: +, length(), show().
  2. Parametric: Your fancy_function() operates on generic or abstract types, providing several concrete types with the same functionality.
    • Examples: print(), getindex(), setindex!().
  3. Subtyping: You allow a symbol (be it a type or a function) to inherit or extend an existing symbol.
    • Examples: Float64 and Int are both concrete instances of the abstract type Real, which in turn subtypes Number.

Polymorphism in OOP

My description of subtyping is phrased somewhat generically because polymorphism can be implemented at different levels. Object-Oriented Programming (OOP) achieves polymorphism primarily through different classes.

  • You can write interfaces and have classes implement. Classes can also extend others. Both are instances of subtyping.
  • Some languages allow fields in a class to be generic. This gives you access parametric polymorphism.
  • Function overloading allows you to implement class-specific methods. This is ad hoc polymorphism.

Example: Cats and Dogs

Here are the type definitions from the JuliaCon example.

abstract type Pet end

struct Dog <: Pet
  name::String
end

struct Cat <: Pet
  name::String
end
  • Abstract types are just nodes in a type tree. It cannot have any fields.
  • Unlike OOP languages, we’re forced to enumerate common fields across concrete types (Cat and Dog).
  • The <: operator is for subtyping; i.e. Cat <: Pet means “Cat inherits from Pet”.

Now let’s add the generic encounter() function.

function encounter(a::Pet, b::Pet)
  verb = meets(a, b)
  println("$(a.name) meets $(b.name) and $verb.")
end
encounter (generic function with 1 method)
  • This is parametric in the sense that we want any Pet subtype to support the enconter() function.
  • Whatever objects we pass, they better have a name field. Julia has no mechanism to enforce this.
  • Ditto for the meets() function call.

Now for the specifics.

meets(a::Pet, b::Pet) = "stares" # generic fallback
meets(a::Dog, b::Dog) = "sniffs"
meets(a::Dog, b::Cat) = "chases"
meets(a::Cat, b::Dog) = "hisses"
meets(a::Cat, b::Cat) = "slinks"
meets (generic function with 5 methods)
  • Idea: We want this function to exhibit a different behavior depending on what kind of Pet objects encounter each other.
  • Notice there is an implied directionality. The order of the arguments matter.
  • The function definitions specializing on types are methods. The code is fairly intuitive.

Let’s test it. Perhaps unsurprisingly, the code does exactly what we expect it to do.

fido      = Dog("Fido")
rex       = Dog("Rex")
whiskers  = Cat("Whiskers")
spots     = Cat("Spots")

encounter(fido, rex)
encounter(fido, whiskers)
encounter(whiskers, rex)
encounter(whiskers, spots)
Fido meets Rex and sniffs.
Fido meets Whiskers and chases.
Whiskers meets Rex and hisses.
Whiskers meets Spots and slinks.

Try it with Python. It has the same flaw as the C++ implementation, and can be fixed using single dispatch. The issue is the granularity for pattern matching in OOP vs that of multiple dispatch.

# Class Definitions
class Pet:
  def __init__(self, name):
    self.name = name

class Dog(Pet):
  pass

class Cat(Pet):
  pass

# Function definitions
def encounter(a: Pet, b: Pet):
  verb = meets(a, b)
  print(f"{a.name} meets {b.name} and {verb}")

def meets(a: Pet, b: Pet):
  return "stares" # generic fallback

def meets(a: Dog, b: Dog):
  return "sniffs"

def meets(a: Dog, b: Cat):
  return "chases"

def meets(a: Cat, b: Dog):
  return "hisses"

def meets(a: Cat, b: Cat):
  return "slinks"

# The example
fido      = Dog("Fido")
rex       = Dog("Rex")
whiskers  = Cat("Whiskers")
spots     = Cat("Spots")

encounter(fido, rex)
encounter(fido, whiskers)

Multiple Dispatch

Julia’s functions support multiple dispatch. You can write a method for a generic function that pattern matches based on none, some, or all of its argument types. There have been programming languages that support multiple dispatch in the past, but Julia is the first to ensure it is a “fast” language feature. Making this work well is non-trivial and is the subject of Jeff Bezanson’s PhD Thesis (Julia co-creator).

Advantages

Expressiveness

An important benefit of multiple dispatch is its expressive power. It lets us write fairly intuitive code. This style turns out to be excellent for numerical code.

Dispatch Type Syntax Arguments Expressive Order Expressive Power
none \(f(x_{1}, x_{2}, \ldots)\) \(\{\}\) \(\mathcal{O}(1)\) constant
single \(x.f(x_{2}, \ldots)\) \(\{x_{1}\}\) \(\mathcal{O}(X_{1})\) linear
multiple \(f(x_{1}, x_{2}, \ldots)\) \(\{x_{1}, x_{2}, \ldots\}\) \(\mathcal{O}(X_{1} \cdot X_{2} \cdot \cdots)\) combinatorial

Interoperability

A consequence of high expressiveness (see the Expression Problem) is the ability to readily extend systems. Lots of packages in the Julia ecosystem are written independently of each other, yet it is common for packages to interact in productive ways with minimal intervention from package authors.

  • Example: Measurements.jl and most packages in the SciML Julia ecosystem “just work”.
  • Example: Compatibility of various packages with ForwardDiff.jl.

Generic vs Specialized Algorithms

It is easy to write generic code without talking about types. Within your own code, you implement specific algorithms by assuming your functions’ inputs support certain functionality; e.g. indexing, iteration, addition, etc. If you notice a trick that accelerate performance based on problem information, it is easy to patch in a better algorithm without re-writing everything. The Julia stack, in turn, may apply further performance optimizations based on your code.

  • Example: See the one-hot vector example in the JuliaCon talk. With a bit of effort, you can turn that code into a versatile one-hot tensor implementation just as in PyTorch.

Symmetry

Notions such as * are either inherently symmetric or multivariate. The single dispatch syntax object.f(x) introduces asymmetry in such cases. For example, matrix-matrix multiplication is not commutative in general there is no reason the evaluation cannot be carried out left-to-right versus right-to-left.

Simpler Design Strategies

This is somewhat subjective. At a minimum, the dynamism in Julia eliminates the need for Gang of Four design patterns, as demonstrated by Peter Norvig’s 1996 critique.

  • Example: OOP languages sometimes use the Visitor Pattern to implement double dispatch.

Separation of Concerns

In Julia, an object is just a struct with type information. Because methods are not “owned” by a class, you’re free to use a combination of generic functions and methods to specialize algorithms on problem information.

  • Example: A \ b uses a polyalgorithm to select the “best” method for solving a linear system based on the data type of A.
  • Example: The HTTP.jl package for client and server functionality has a careful and composable approach to designing its request() function.

Disadvantages

Compilation Penalty

The Julia Stack must handle an incredibly large number of function definitions. That means the JIT compiler must quickly compile new functions and methods, especially when calling a function for the first time or after loading packages.

  • Historically, running using Plots and generating a plot was painfully slow compared to other dynamic languages.
  • Lots of work in this area, such as pre-compilation, to reduce the “Time To First Plot” problem.
  • Little control over this issue as a user. As a developer, you can write your packages to support pre-compilation.

Method Ambiguity

It is “easy” to write ambiguous method definitions. For example:

f(x::Number, y::Any) = "A"
f(x::Any, y::Number) = "B"
f (generic function with 2 methods)

Trying to use f() as written will trigger a MethodError.

Type Piracy

It is “easy” to accidentally overwrite existing methods, which is especially bad if you do it on methods or types you did not write yourself. This can silently break the functionality of a package.

  • Fix: Only overload functions on types that you own. Use your own function names for types you do not own.

Discoverability

Finding methods in single dispatch systems by typing x. is easy. In Julia’s multiple dispatch system, you rely on people writing good documentation so that object? or ?method helps you discover other methods.

Design Strategies

Leverage Type Information

The “fix” for the type instability in the for loop example is to use type information. Type annotations are the wrong tool to reach for here. Instead, programmatically access types with various functions:

function mysum(x::Vector{Float64}) # bad
  s = 0.0
  for xi in x
    s += xi
  end
  return s
end
function mysum(x::Vector{T}) where T # bad
  s = zero(T)
  for xi in x
    s += xi
  end
  return s
end
function mysum(x)
  s = zero(eltype(x))
  for xi in x
    s += xi
  end
  return s
end
  • We assume x is some kind of container that supports iteration, with a common type.
  • Use eltype() to retrieve type of elements stored in x.
  • Use zero() to use correct zero specific to element type.

Traits (Advanced)

Certain programming languages, notably Rust, allow objects to hook into multiple interfaces at once. Tom Kwong’s book has several examples explaining this concept in Julia, even though the language does not have formal support for the feature (due to technical issues). Briefly, a trait is a behavior a Julia type supports, formalized through a separate type. The idea is to use a trait type to determine whether an object supports a particular behavior, allowing you to formalize an interface.

Let’s illustrate this with our Pet objects. We’ll add a new concrete Pet type without a name field and define a trait to let us safely use it in our encounter() method.

# This trait is binary. Either you've got it or you don't.
struct HasName end

HasName(::Pet) = false # default
HasName(::Dog) = true
HasName(::Cat) = true

# A new Pet...
struct Roach <: Pet end

meets(a::Roach, b::Pet) = "scurries"

# Safely access the name field. I would not use this in practice.
getname(a::Pet) = HasName(a) ? a.name : "Nameless Creature"

# overwrite the original definition; must match signature!
function encounter(a::Pet, b::Pet)
  verb = meets(a, b)
  println("$(getname(a)) meets $(getname(b)) and $verb.")
end

# Examples
encounter(fido, rex)
encounter(Roach(), fido)
encounter(fido, Roach())
Fido meets Rex and sniffs.
Nameless Creature meets Fido and scurries.
Fido meets Nameless Creature and stares.

Julia’s iterator interface uses the IteratorSize trait, which takes different values. In particular, the value IsInfinite() for this trait allows you to implement support for infinite objects. See the InfiniteArrays.jl for an interesting application of this trait.
