Minimizing Functions of Residuals

Consider the generic problem

\[ \min_{\boldsymbol{\beta}}~\sum_{i=1}^{n} \rho\left(y_{i} - \sum_{j=1}^{p} x_{ij} \beta_{j}\right), \]

where \(\rho(r)\) is a suitably chosen function.

  • The choice \(\rho(r) = \frac{1}{2}r^{2}\) is ordinary least squares (OLS).
  • The choice \(\rho(r) = |r|\) gives median regression.
  • The Huber loss (defined below) gives an estimator robust to outliers. It smoothly interpolates between the squared loss and the absolute value loss.

\[ \rho_{c}(r) = \begin{cases} \frac{1}{2} r^{2} & |r| \le c \\ c (|r| - \frac{1}{2}c) & \text{otherwise} \end{cases}. \]

Make the problem concrete with data

Let’s simulate some data \((y_{i}, \boldsymbol{x}_{i})\):

  • Set the number of samples \(n = 100\)
  • Set the number of features to \(p = 2\). We’ll treat \(x_{i1}\) as the intercept “feature” and \(x_{i2}\) as a proper independent variable.
  • Simulate \(x_{i2} \sim \mathcal{N}(0, 1)\), i.e. each instance of the independent variable follows the standard normal distribution.
  • Set the “ground truth” as \(\beta_{0} = -3\) and \(\beta_{1} = 2\). We’re working with a parametric model so knowing \(\beta\) completely determines the model.
  • Set \(y_{i} = \boldsymbol{x}_{i}^{\top} \beta + \epsilon_{i} = \beta_{0} + x_{i2} \beta_{1} + \epsilon_{i}\). Here \(\epsilon \sim \mathcal{N}(0,1)\) as well.
n = 100
p = 2
X = randn(n, p)
X[:, 1] .= 1
beta = [-3.0, 2.0]
y = X * beta + randn(n)

Remember that in linear regression analysis, we are modeling the conditional mean \(E[Y \mid X] = \beta_{0} + \beta_{1} X\); i.e. \(X\) is given and the goal is to determine \(\beta\) to fully specify the model for the conditional mean.

  • The simulation above establishes the “ground truth”. We fully simulated the data generating process.
  • Fitting \(\beta\) using least squares; i.e. \(\rho(r) = \frac{1}{2} r^{2}\) gives a particular estimator.
  • In principle, we can choose any model for \(\rho(r)\) to fit a model. Optimization + Statistics gives us a way to derive estimators with certain desirable properties.
  • The OLS estimator gives us the best linear unbiased estimator (BLUE) for \(\beta\). Follows from Gauss-Markov theorem under certain assumptions. Anything else will be biased in the sense that \(E[\hat{\beta} \mid X] \neq \beta\).
# xmin, xmax = extrema(X[:, 2])
scatter(X[:, 2], y)

Implement the estimator for OLS

Questions to reflect upon before writing code

  • What is the optimization model I need to implement? That is, what is the loss/utility function?
  • What are the required inputs? That is, what information does the caller/user need to tell me?
  • How do I predict from the statistical model?
  • How do I measure errors from the model?
function ols_loss(y, X, b)
  # predict from the model
  model_prediction = X * b

  # obtain the residuals
  r = y - model_prediction

  # apply transformation of residuals + aggregrate
  return sum(1/2 * r .^ 2)
end

We wrote a function so let’s test that it does something sensible when we invoke it:

ols_loss(y, X, zeros(2))

This should just be \(\frac{1}{2} \sum_{i} y_{i}^2\):

ols_loss(y, X, zeros(2)) ≈ 0.5 * sum(abs2, y) # applies transformation to y[i]'s

Is it compatible with ForwardDiff? After all, we don’t want to spend our lives writing down gradients unless we really need to:

ForwardDiff.gradient(ols_loss, zeros(2)) # won't work

What went wrong???

  • Start at the top of the message.
  • Gives us a hopefully informative error.
  • To find where everything collapsed, look at the stacktrace:
    • Top: this is the innermost function call (i.e item [1]). Shows types inferred in the function call + line numbers indicating location of error.
    • Middle: Lots of intermediate function calls.
    • Bottom: this is the outermost call; usually points to our source code in a Quarto document (or “line” in a REPL).

The error message tells us that Julia cannot evalute ols_loss() as a function of 1 argument. Use an anonymous function to make it a 1 argument function:

ForwardDiff.gradient(b -> ols_loss(y, X, b), zeros(2))
  • The y and X are implict from the enclosing scope.
  • Be careful with anonymous functions! In any language, they have a cost paid by the “global” reference.
    • Doesn’t matter too much in R where function calls are “expensive” anyway.
    • In Julia this can introduce heavy bottlenecks due to stress applied to its compiler.
    • Later we’ll see a way to avoid paying the penalty.

Implement an algorithm

We’ll use gradient descent with a backtracking linesearch.

Before we start writing code

  • What is the optimization model?
  • What is the algorithm map?
  • What assumptions will I make (to simplify coding) and impose on the caller/user?

Outlining the implementation

  • Our assumptions translate to “interface” in deciding what to put in the function signature.
  • We started “inside the loop”. How do we stop?
    • Limit number of iterations.
    • Check that \(\nabla f(\boldsymbol{x}) \approx 0\) in some sense. How? Use norm of gradient since \(\|\boldsymbol{v}\| = 0\) if and only if \(\boldsymbol{v} = 0\).
  • Semicolon: everything to the right is a keyword argument
  • Keyword arguments should have type annotations i.e. keyword::SomeType = default_value.
  • How do we know it’s working? Need to check gradients. \(\nabla f(\boldsymbol{x}) \approx 0\) is a requirement for a minimum.
  • for vs while: choice will dictate how you keep track of the algorithm’s state.

Making changes

  • Generally a good idea to report some information about how well the algorithm performed.
    • Number of iterations
    • The solution itself
    • Gradient or norm of the gradient
    • Convergence history
  • Print statements are okay, but users should have a way to disable them. They do incur a cost! Common approach: add a parameter verbose::Bool = false to conditionally print information.
  • Returning a single “result object” vs a Tuple.
    • Named tuples are a good compromise.
    • Avoids the user having to write code like niter, estimate, other_info = solver()
    • In R, use list() construct. Literally what lm() and similar model fitting functions use to construct reports in the language.
# loss: This is a function-like object, 1-arg, compatible with ForwardDiff
# x0: initial guess
# This function minimizes the loss function and returns the solution x
function gd(loss, x0; maxiter::Int = 100, tol::Real = 1e-3, nsteps::Int = 10)
  # x = x0 # variable assignment
  x = copy(x0) # make a copy of the caller's input
  grad = ForwardDiff.gradient(loss, x) # initialize gradient

  niter = 0
  for iter in 1:maxiter
    niter = iter
    # linesearch
    t = 1.0
    for m in 1:nsteps
      # if we succeed in decreasing the objective
      if loss(x - t * grad) < loss(x)
        break
      else # otherwise
        t = 1/2 * t
      end
    end

    @. x = x - t * grad
    grad .= ForwardDiff.gradient(loss, x) # evaluate gradient at current estimate
    converged = norm(grad) < tol # is gradient close to 0
    if converged
      break # break out of innermost loop
    end
  # not_done = iter < maxiter
  end
  result = (;
    iterations = niter,
    solution = x,
    gradient = grad
  )
  return result
end

We wrote a function, so let’s test it!

loss = b -> ols_loss(y, X, b)
result = gd(loss, zeros(2); maxiter = 100, tol = 1e-3)
  • Access fields in the NamedTuple with result.<fieldname>; e.g. result.solution delivers the estimate \(\hat{\beta}\).
  • Close to the ground truth.
  • Is it a good estimate? Can compare to OLS solution delivered by X \ y. However, sometimes there are no reference tools to compare against.
  • What would happen if we made the noise terms \(\epsilon_{i}\) large?

Reflection

  • The gd() code has little if any problem-specific information contained in it. The function encapsulates the problem of minimizing a loss function.
  • Similarly, ols_loss() function has little to do with minimization. It simply reports the OLS loss.
  • In writing good, reusable code we strive for such separation of concerns.
  • Makes our code composable, especially in a language like Julia.
  • Same principles apply to writing code for data analysis (vs implementing methodology). Use functions rather than writing large, hard-to-follow scripts.

Try it on a different problem

Implement the Huber loss.

function huber_loss(y, X, b; c = 0.25)
  # predict from the model
  model_prediction = X * b

  # obtain the residuals
  r = y - model_prediction

  # apply transformation of residuals + aggregrate
  tmp = @. ifelse(
    abs(r) <= c,  # condition
    0.5 * r ^ 2,      # if true
    c * (abs(r) - 0.5*c) # if false
  )
  return sum(tmp)
end
  • Code is very similar to the OLS code.
  • Only meanginful changes are:
    • Loss has a parameter c that we should account for. Here we implement it as a keyword argument.
    • The residual transformation changes slightly.
    • Challenge: Implement the Huber function efficiently and without the allocation we have above.

We wrote a funciton, so let’s test it.

huber_loss(y, X, zeros(2))

Now test our gd() function on the new problem:

result = gd(b -> huber_loss(y, X, b), zeros(2);
  maxiter = 10 ^ 3,
  tol = 1e-3,
  nsteps = 20
)

In class

  • Did not converge with maxiter = 10 ^ 2 and nsteps = 10. Suggested that we try a larger iteration budget like maxiter = 10 ^ 3.
  • Larger iteration budget did not work either. Maybe backtracking was failing, so we try nsteps = 20.
  • Noticed that gradient was not going towards 0. Points to a problem in our code. Indeed, Dr. Landeros forgot to square r in the abs(r) <= c branch of the code.

More Reflection

  • Ideally, we can use a library/package to solve our problem.
  • HW3 + HW4 should serve as examples to you that developers of stats/ML software cannot address every possible variation of a problem.
  • Practitioners ((data) scientist, statistician, ML engineer…) need to have some knowledge of algorithms + theory.
    • Example: How do I know gradient descent will work on my problem?
    • Example: Do I need a solver with step size control (backtracking)?
    • Example: Can I design my loss function to be “efficient”, making it easy for AD + black-box solvers to evalute it and its derivaties?
    • Example: What can I check to make sure an algorithm is working properly on my problem/data?
  • For us, main takeaway from this exercise is to understand the “levers” we can control in a relatively simple algorithm like gradient descent.

Identifying Scaling Laws

Use this as a running example for next time.

Fact: Bigger cities tend to produce more economically per capita.

Geoffrey Brian West and his colleagues proposed power law relationships as a means to study emergent phenomena in urban centers. For example, consider the model

\[ Y = y_{0} N^{a} + \text{noise}, \]

where \(Y\) is the per-capita “gross metropolitan product” of a city, \(N\) is its population size, and \(y_{0}\) and \(a\) are parameters to be determined.

TipSome References

Bettencourt LM, Lobo J, Helbing D, Kühnert C, West GB (2007). “Growth, innovation, scaling, and the pace of life in cities”. Proc Natl Acad Sci. 24;104(17): 7301-6. doi: 10.1073/pnas.0610172104.

West, GB, Brown, JH, Enquist, BJ (1997). “A general model for the origin of allometric scaling laws in biology”. Science. 276(5309): 122-126.

Desai-Chowdhry, P, Brummer, AB, Savage, VM (2022). “How axon and dendrite branching are guided by time, energy, and spatial constraints”. Scientific Reports, 12(1), 20810.
